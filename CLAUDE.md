# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
A single-admin PDLC assistant (POC): an OpenAI-backed chat that turns product intent into Requirements, a Design with an architecture diagram, and later code, with **living traceability** (a requirement or code change updates the design diagram). The headline experiment is **reverse engineering a design from three inputs: a requirements.md, chat, and existing code**. Explicitly out of scope: multi-user, automated tests, observability.

[PLAN.md](PLAN.md) (scope, architecture, phases) and [tech-stack.md](tech-stack.md) (decided stack) are the source of truth for the *target*; keep them consistent with each other. The build is proceeding in a simplified order (the approved plan is outside the repo): steps 0–5 are done (spike, md model, LLM gateway, md→diagram, requirements.md→design, minimal UI) plus step 6 (streaming chat: questions, requirements documents and design change requests); step 7 (code→design) is built in a first cut (see **Code to design** below); its Phase C extras (DI resolution, foundation band, cross-project linking) and step 8 (evaluate) are next. Open decisions are at the bottom of PLAN.md and tech-stack.md; update them when decided.

**Current reality vs. the docs:** storage is a local folder (`pdlc.storage.mode=local`, S3 is not implemented), no SQLite/budgets/cache yet, no Docker/Caddy/S3/CI. Do not add Postgres, Redis, queues, ECS, Cognito, CI/CD or IaC unless asked (tech-stack.md §8). `AGENTS.md` is a stale copy of an older CLAUDE.md; this file is authoritative.

## Commands
Windows; use Git Bash and `./mvnw` (Maven is not on PATH). Backend is Java 17 (do not assume Java 21 features) on Spring Boot 4.0.x (start.spring.io no longer offers 3.x). Frontend is plain JavaScript/JSX (no TypeScript), React 19, Vite, Tailwind v4. Local Node is v20 (the docs say 22; Archify needs ≥18). `GET /api/health` is the one unauthenticated endpoint (handy to check the backend is up).
- Backend: `cd backend && ./mvnw spring-boot:run` (port 8080; add `-Dspring-boot.run.arguments=--server.port=8081` for a second instance). `PDLC_DATA_DIR` sets the project folder (default `./data/projects`, gitignored). Login `PDLC_ADMIN_USER`/`PDLC_ADMIN_PASSWORD`, default admin/admin.
- Dev servers may already be running (check `netstat -ano | grep -E ':(8080|5173) '` before starting): the Spring Boot dev process is not hot-reloaded, so a backend started before your change serves old code (restart it; Vite hot-reloads). Use another port rather than killing a process you did not start. After `npm install` of a new package, Vite reloads the page once while it re-optimizes dependencies.
- Compile only: `cd backend && ./mvnw -q -DskipTests compile`
- Frontend: `cd frontend && npm run dev` (http://localhost:5173, proxies `/api` to 8080; `PDLC_BACKEND=http://localhost:8081` retargets it), `npm run lint`, `npm run build`
- Tests: there are no automated tests by design (manual smoke checks only); only the generated context-load test exists (`./mvnw test -Dtest=PdlcAssistantApplicationTests`).
- Archify CLI (run from repo root, never from inside `tools/archify`): `node tools/archify/archify/bin/archify.mjs validate|deliver architecture <ir.json> [out.html]`
- LLM gateway smoke check (needs a key): `cd backend && ./mvnw -q compile dependency:build-classpath -Dmdep.outputFile=target/cp.txt`, then `java -cp "target/classes;$(cat target/cp.txt)" com.pdlc.assistant.spike.GatewaySpike` (normal call, oversize rejection, single retry).
- **API key:** `pdlc.llm.api-key` defaults to the `OPENAI_API_KEY` env var; for local dev put it in the gitignored `backend/config/application.properties` (Spring Boot loads it when started from `backend/`). Never in the tracked `application.properties`. The app starts without a key (the client bean is lazy).

## Architecture (what exists)
Backend `backend/src/main/java/com/pdlc/assistant/`, layered by package: `controller/`, `service/`, `dto/`, `model/`, `repository/` (storage interface, `repository/impl/` for implementations; `interface` is a reserved word so it cannot be a package), `mapper/`, `config/`, `exception/` (one `@RestControllerAdvice`: IllegalArgument→400, Diagram→422, Llm→502), `spike/` (throwaway). Put new code in the matching layer.

How the pieces fit (needs several files to see):
- **Markdown files are the model.** `ProjectService` owns a project folder: `docs/04-technical-requirements.md` (`REQ-###`) and `docs/11-building-blocks.md` (`CMP-###` with `layer`, `satisfies`, `links`, `responsibility` attrs), `changelog.md`, `.pdlc/history/` backups, derived `diagrams/`. `model/MdDocument` is a line-based parser/patcher: it edits entries by ID and never rewrites other content. Entry format is `- CMP-001: Name` plus indented `- key: value` lines.
- **All writes are patches.** `PatchOp` (add/update/remove by ID) → `ProjectService.previewAll/applyAll` apply them to in-memory docs, validate the *combined* REQ+CMP state (ID prefixes, `layer` ∈ `model/Layer`, `satisfies`→existing REQ, `links`→existing CMP), then back up, write, bump `version`, append the changelog. Multi-file sets are all-or-nothing. Every patch endpoint has `?dryRun=true`; nothing is written until the admin applies. Undo restores the latest backup per file.
- **Diagram is derived.** `DiagramService.render` → `mapper/ArchitectureIrMapper` (deterministic md→Archify IR) → `ArchifyRunner` (Node subprocess in a temp dir, `deliver` validates then renders, 60 s timeout, update check disabled) → `diagrams/architecture.{ir.json,html}`. `GET /api/projects/{id}/diagram` re-renders on every call, so it cannot be stale.
- **All LLM calls go through `service/LlmGateway`** (`complete(LlmRequest, SchemaClass)` for structured output, `stream(...)` for token-by-token text, which cannot be retried and stops when the caller's `cancelled` flag turns true): schema-enforced via the Java class (use enums for closed value sets), pre-flight input cap (~chars/4), output cap, one retry on bad output, token log. Never call the OpenAI client elsewhere. Settings: `pdlc.llm.*`.
- **requirements.md → design** (`RequirementsImportService`): `RequirementsSplitter` compacts the md locally; one gateway call returns requirements and components under the model's own keys (r1.., c1..); the backend assigns real REQ/CMP ids, resolves references, adds deterministic warnings (unsatisfied REQ, isolated component, dropped unknown reference), dry-run renders via Archify, and returns a proposal `{patches, files, warnings}` that is applied by posting `patches` to `/patch-set`. Add-only. Extraction is non-deterministic (see spike/README.md); the warnings and Apply/Reject are the safety net. Sample input: `spike/samples/todo-requirements.md` (now a 166-line enterprise SRS, ~2.3k tokens, under the 6000-token input cap; not yet run through the import, so expect more components and more warnings than the earlier 1 KB todo sample).
- **Streaming chat** (`ChatController` → `ChatService`): `POST /api/projects/{id}/chat` body `{message, history, mode}` returns SSE (`SseEmitter`, work on the `chatExecutor` pool) with events `status {text}`, `token {text}`, `proposal {summary, patches, files, warnings}`, then `done` or `error {message}`. Three routes: (1) a requirements document (`mode: "requirements"`, or ≥2 markdown headings or ≥800 chars) → `RequirementsImportService`; (2) a design change request → `DesignChangeService`; (3) anything else → a streamed answer from a compact listing of the REQ/CMP entries. `IntentRouter` decides 2 vs 3: plain wh-/yes-no questions ending in `?` skip the model; otherwise a ~250-token schema-enforced call on `pdlc.llm.router-model` (default gpt-4o-mini), biased to "question" because a wrong question is harmless and a wrong change is not; if it fails, treat as a question. The server keeps no chat state. If the client disconnects (Stop), `ChatController` sets `cancelled` and the gateway closes the OpenAI stream. Errors after streaming has started arrive as an `error` event, not an HTTP status.
- **Design change from chat** (`DesignChangeService`): `ModelSlicer` sends an outline of every REQ/CMP plus full detail only for entries whose keywords match the message and their 1-hop neighbours (deterministic, no LLM). The model returns `DesignChangeDraft`: add/update/remove ops where new entries carry keys n1.. and links/satisfies are edited with explicit `addLinks/removeLinks/addSatisfies/removeSatisfies` lists (so an update can never wipe existing links); empty string / `keep` mean unchanged. The backend assigns real ids, merges lists into the current entry, drops no-op updates, cleans references left dangling by a removal, then `previewAll` validates it as one set. Warnings: new component not linked, new REQ unsatisfied, any removal. `ProposalBuilder` (shared with the import) builds the diff and dry-run renders via Archify. Prompt rules that mattered (gpt-4o-mini): the CALLER lists the callee (with a Redis example), refine an existing REQ instead of adding an overlapping one, return empty lists for questions/vague requests. Cost per change is about 1.2–1.4k prompt and under 300 completion tokens (intent + change call).
- **Product interview** (`DiscoveryService`, `model/NarrativeDoc`, `model/MdSections`): until requirements exist, every chat message is part of an interview that fills `docs/01-product-intent.md`, `02-personas.md`, `03-user-stories.md` (created as `status: empty` templates by `ProjectService.create`; older projects get them lazily). Per message: (1) a schema-enforced `DocSyncDraft` call returns small edits (`set`/`add`/`remove`/`removeSection`, one line each, per file+section) which `MdSections` merges deterministically (validates Product Intent headings, assigns `US-###` ids, dedupes); whole-document rewrites were tried first and gpt-4o-mini wiped earlier content, so do not go back to them; (2) a streamed reply acknowledges and asks the next question. These docs are written directly (backup, version bump, changelog, `undo` works) and announced with an SSE `docs {files}` event; this is the one place chat writes without Apply. "generate requirements" (regex in `ChatService`, checked before the interview) feeds the three docs to `RequirementsImportService` (or, if requirements exist, to `DesignChangeService` as a re-alignment). Once requirements exist the router's `product` intent sends product-level changes through the same interview path: docs are updated first, then a `DesignChangeService` proposal is built from the change note so REQ/CMP follow the intent. `pdlc.llm.discovery-model` (env `PDLC_DISCOVERY_MODEL`) can point the edit call at a stronger model; gpt-4o-mini sometimes leaves stale text in other sections after a change of mind, gpt-4o was clearly better. `GET /api/projects/{id}/files` feeds the explorer. **Section-by-section flow** (`model/InterviewStep`): the product part of the interview is 8 ordered steps (Vision, Problem, Target users, Goals, Scope, Constraints, Personas, User stories), followed by the technical steps below, each with an "enough when" test. After the edit call, a separate small `StepCheck` call (met + missing) judges only the current step; a completed step is stored as `done: VISION, ...` in the doc front matter, can only complete when its section has content, at most one step completes per message, and a step whose section gets emptied reopens. The "✅ X is captured" line and the final "generate requirements" message are emitted by the backend (the model mislabelled them and copied the pattern from history, so ✅ lines are stripped from history). The edit call is told the current step, otherwise gpt-4o-mini files answers under Vision. Completion as a field of the big edit schema did not work (the model left it empty), keep it a separate call. SSE `progress {steps}` and `GET /api/projects/{id}/interview` feed the progress strip in ChatPanel.
- **Code to design** (step 7; chat "sync code" or "sync code from <folder>", `CodeSyncService`): deterministic first, the LLM only names. (1) `CodeInventoryService` walks the folder (skips node_modules/target/tests, caps `pdlc.code.max-files`), SHA-256 hashes sources and matches manifests (pom.xml, package.json, application.yml, docker-compose...) against `resources/code-rules.yml` for external systems with file:line evidence. (2) `CodeExtractorRunner` runs `tools/extract/extract.mjs` (Node, `web-tree-sitter` **0.22.6** with `tree-sitter-wasms`; newer web-tree-sitter cannot load those grammars) only on files whose hash changed and returns imports, types, annotations, routes, entities, outbound URLs with lines; `npm install` in `tools/extract` first. Facts are cached in `.pdlc/facts.json` (per source folder). (3) `CodeGraphService` resolves imports to files (Java by package+type, JS by relative path), clusters by package/folder (common Java package prefix stripped, one split level for a dominant folder, folded to `pdlc.code.max-components` with a "misc" cluster) and aggregates edges caller to callee; layer is decided here (Java=backend, JS without routes=frontend, security by name), the model may only promote to security. (4) `CodeLabelService` sends a few lines of facts per cluster in one schema call (name, responsibility, satisfies REQ ids), cached in `.pdlc/labels.json` by facts+REQ hash. (5) `CodeSyncService.reconcile` matches clusters to CMPs by the `code:` attr (clusters by key, externals as `ext:<Name>`; a designed CMP with the same name is adopted and gets `code:`), emits add/update/remove ops plus a drift report (code with no REQ, designed CMP with no code, unsatisfied REQ). Designed links are never dropped, only links to removed components; unchanged re-sync costs no model call. Proposal goes through `ProposalBuilder` (Apply/Reject card); an already-matching design is returned as plain text. The folder is any local path (admin-only POC, do not expose to other users); with no path it reuses the last one or `<project>/implementation`. Known limits: same-package Java references without an import are not seen, dynamic URLs and reflection are invisible, cluster keys can change when a folder's share of the module crosses the split threshold, foundation band / DI resolution / cross-project URL linking are not done.
- **Diagram fallback** (`DiagramService.renderResilient`): when Archify rejects connections for edge-through-node, only those connections are dropped (up to 3 rounds), the title says "N links not drawn" and the proposal warns; the links stay in the md. `ArchitectureIrMapper` wraps a layer wider than 5 into several rows, ordered by dependency depth.
- **Technical interview** (steps 9-15 of `model/InterviewStep`, doc `docs/05-technical-decisions.md`): after the product steps the interview continues with Architecture, Frontend, Backend, Database, Caching, Auth, Deployment (same step check, up to 4 steps per message). The doc is part of `combinedDocuments`, so "generate requirements" turns it into REQs ("The backend is written in Java 17 with Spring Boot 3") and into components carrying `language` and `technology` attrs; `ArchitectureIrMapper` shows technology as the sublabel and language as the `tag`. The router counts stack choices ("add Redis caching", "use PostgreSQL") as `product`, so after requirements exist they update the tech doc first and then cascade into a design-change proposal.
- **Code generation = skeleton** (`CodeGenService`, chat "generate code"): a high-level scaffold in `<project>/implementation/`, not a finished app; users write the real code on top. One plan call (files, each with component and a short api) then one call per file; each component's main class imports the classes of the components it links to; manifests (`pom.xml`, `package.json`) are written last from the libraries tree-sitter finds imported. A gap pass uses tree-sitter facts (`usedTypes`, unresolved project imports and relative JS imports) to generate files the plan forgot; a syntax pass rewrites files tree-sitter marks `partial`. `GenerationRecord` (`.pdlc/generated.json`) stores component and hash per file: regenerate never overwrites a file the user changed, and `CodeGraphService` clusters generated files as `cmp:<CMP-id>` so a sync maps the code back onto the designed component instead of inventing new ones. Output is not compiled or tested; a Maven compile-and-repair loop was tried and removed. `pdlc.llm.codegen-model` (env `PDLC_CODEGEN_MODEL`) can use a stronger model.
- **Code watcher** (`CodeWatchService`, `pdlc.code.auto-sync`, `pdlc.code.poll-ms`): polls a cheap fingerprint (count, size, newest mtime) of each synced source folder; when it changes and is stable for one more poll it runs `CodeSyncService.syncAndApply` (changed files only, applied at once; backup, changelog and Undo still work) and bumps `version` in `.pdlc/autosync.json`. `GET /api/projects/{id}/code/status` exposes it; `useCodeSync` polls every 5 s and reloads diagram and files. Verified scenarios (skeleton + manual edits): new dependency between components adds a link; a new package becomes a new component with a link from its caller; a new library in `pom.xml` adds an external component linked from the class using it; deleting a package removes its component and links; idle changes nothing. Deleting all code of a designed component keeps it (design is intent) and reports drift. Externals that no file imports attach to the entry cluster, else the largest backend cluster.
- **Frontend** (`frontend/src/`): `api/` (all calls go through `apiClient.js`; `projectApi.js`), `hooks/` (`useAuth`, `useProjects`, `useDiagram`, `useChat` hold all state logic), `components/chat|diagram|explorer|editor`, `hooks/useCodeSync` (polls `/code/status` and reloads diagram and files), `pages/` (LoginPage, WorkspacePage: file explorer left built from `GET /files` via `explorer/workspaceTree.js`, md/code/diagram tabs in the center, chat right). Chat history is in memory only and is sent back (last 6 turns) with each message; `api/sse.js` reads SSE over `fetch` because EventSource cannot POST or send the auth header; leaving a project mid-reply aborts the stream.

## Windows / environment quirks
- The repo root is not a git repository (only `tools/archify` has its own `.git`), so there is no version control for code edits; `Undo` in the app only covers project md files, not source.
- Git Bash `/tmp` is not the path Node sees (`C:\tmp`); put scratch files under the repo's `backend/target/` or a Windows temp path when mixing curl and node.
- `tools/archify` is a full clone with its own `.git`; do not run anything from inside it (Interpreters load code from the cwd).
- Browser-level UI checks used headless Edge driven by `puppeteer-core` (installed in a temp dir outside the repo): launch `msedge.exe --headless=new --remote-debugging-port=9333 --user-data-dir=<tmp>` yourself and `puppeteer.connect({browserURL})`; puppeteer's own `launch` fails on this machine. Each new tab has empty sessionStorage, so log in again, and wait for the new project to be *selected* after Create (a project switch remounts the chat and clears it).

## Security-relevant design
Single admin from env config. The SPA sends an explicit `Authorization: Basic` header with `credentials: 'omit'`: no cookies, no browser Basic-auth prompt. `SecurityConfig` exempts requests carrying an `Authorization` header from CSRF, which is only safe because browsers never auto-attach it, so do not switch the frontend to browser-managed Basic auth or cookie sessions without revisiting that. The diagram needs the header, so it is fetched and shown in a `sandbox="allow-scripts"` iframe via `srcDoc`; `SecurityConfig` also allows same-origin framing.

## Archify gotchas (all learned the hard way)
- Layout is not automatic: set `"layout": {"mode":"grid","cols":N,"cellW":180}` with per-component `row`/`col`; without positions rendering crashes even though schema validation passes.
- Labels wider than the box are rejected (boxes are 180px; the mapper truncates labels to 25 chars); connection labels that overlap boxes are rejected (the mapper emits none).
- Do NOT set `fromSide`/`toSide`: forcing sides made edges cross components in the same column; Archify auto-routes.
- Component `type` is a fixed enum matching `model/Layer` (frontend, backend, security, messagebus, database, cloud, external); the enum order is the diagram row order.
